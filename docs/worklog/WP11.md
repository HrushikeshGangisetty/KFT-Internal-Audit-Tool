## Done

### WP11 — releases and dual authenticated approval (`fcops/backend/releases/`)
- New `releases` app: `Release(product, version, legacy, created_by)`, `ReleaseRevision(release, number, source_ref, artifact_ref, artifact_sha256, internal_notes, recipient_notes, compatibility, known_limitations, content_hash, created_by)` and `ReleaseApproval(revision, role ∈ software_head/manager, actor, decision ∈ approve/reject, comment, at)`, unique `(revision, role)`. Revisions and approvals refuse `save()` on existing rows and `delete()`.
- `services.approval_state()` computes approved / rejected / pending / legacy from the rows; "current approved revision" is the latest revision when approved, never a stored flag. Approved needs both roles from two distinct people.
- `services.decide()`: locks the release; checks the actor holds the role's capability grant **at decision time** (`is_software_head` / `is_manager`; being an admin or a head of another department is not enough); latest revision only; rejection needs a reason and blocks further decisions on that revision; the same person cannot approve in both roles; legacy revision 1 cannot be approved retroactively.
- Drafting (`create_release`, `revise`) needs `can_draft_release`. An edit is a new revision (no-op edits refused by content hash); earlier revisions and their approvals are kept. Creating a release still registers the version in `fc.SoftwareVersion` so tester dropdowns stay in step.
- **Legacy data:** `releases/migrations/0002_legacy_software_updates.py` copies every `fc.SoftwareUpdate` row to `Release(legacy=True)` with one revision (`source_ref` = git SHA; release notes plus "Legacy approver field: <name> (<time>) … not an authenticated approval" in `internal_notes`; `recipient_notes` empty). No approval rows are created. The old table is left in place, unchanged.
- **Old named-approver path retired:** `/api/software-updates/` (and `approvers/`), `push_software_update`, `CanPushSoftwareUpdate`, `User.can_push_software_update` / `can_approve_software_update` and the `/me` flags for them are removed; the `PushUpdate` page is replaced by `Releases` and `/software/push-update` redirects to `/releases`. The `SoftwareUpdate` model stays as the source record.
- `Task.release` (nullable, scoped input) added — the link WP10 deferred (`tasks/migrations/0002_task_release.py`).
- `/api/auth/me/` gains display-only `can_draft_release`, `can_send_announcements`, `release_approval_roles` from grants.

### WP12 — recipient source (`releases/recipients.py`)
- `SyntheticRecipientSource`: segments `pilot-testers` (3), `all-gcs-users` (8) and `simulate-failure` (always errors, for demonstrating the failure state); every address is `gcs-user-NNN@example.invalid`, names say SYNTHETIC.
- `SignupApiRecipientSource` is a stub that **returns an error** ("contract is pending"); no request shape, field names or credentials are invented. Selected only when `SIGNUP_API_ENABLED=true` (default false).
- `validate()` treats rows as untrusted: one invalid email or missing/repeated id fails the whole fetch. Any error → `WorkflowError(recipient_source_failed)`, no snapshot, no campaign; there is no fallback list.
- `RecipientSnapshot` (immutable) stores source, `synthetic`, segment, fetched_at/by, recipients, count.

### WP13 — campaigns (`releases/services.py`, `views.py`)
- `Campaign` and `CampaignDelivery` as planned, plus append-only `DeliveryAttempt` rows (send / retry / reconcile, with actor and error) as the per-recipient attempt history.
- Preview (`POST /api/campaigns/preview/`): sender capability, current approved revision, fresh snapshot; renders subject/text/HTML from product, version and `recipient_notes` **only**; stores a draft; nothing is queued.
- Send (`POST /api/campaigns/<id>/send/`, idempotency key): under a row lock rechecks capability, current approval and snapshot age (`CAMPAIGN_SNAPSHOT_MAX_AGE_MINUTES`, default 60); creates one delivery per recipient and enqueues one job each (on commit, via the WP3 queue). Same key again → same campaign; a different key on a sent campaign → 409 `already_sent`.
- Delivery job `campaigns.deliver`: skips anything not `queued`; one message per recipient (single `To`, no CC); SMTP recipient/sender/data refusals → `failed`, any other exception → `unknown`; never raises, so there is no automatic resend.
- `retry/` re-queues only `failed`; `reconcile/` settles an `unknown` delivery as `accepted` or "confirmed not sent" (→ `failed`, retryable) with a required note; `resend/` needs a reason and creates a new linked draft with a fresh recipient list. Campaign status settles to completed / completed_with_failures.
- Scope (`access/policy.py`): releases and approvals readable by all authenticated staff; campaigns, deliveries and recipient lists only with `can_send_announcements` or `can_view_customer_contacts`; `Campaign`/`CampaignDelivery` audit entries hidden from others.

### Frontend
- `pages/Releases.jsx` (list, draft form, detail): revision content, state tag ("Legacy — not approved under current process"), approval history, Approve/Reject buttons only for the roles in `release_approval_roles`, edit → new revision, and for senders the announcement card: SYNTHETIC banner, segment picker, preview with exact subject/body and recipient list, Send (one `crypto.randomUUID()` key per draft), delivery table with Retry failed, Reconcile unknown and Resend. ## Decisions taken in this session (and why)

- Approval order is not enforced (either role may decide first); PRD §15 leaves order, absence and delegation open. Both roles must be held by distinct people; nothing else is assumed.
- The email template uses product, version and `recipient_notes` only, as the plan states; compatibility and known limitations are not sent until someone decides they are recipient-facing.
- Any rejection ends that revision; the release needs a new revision (plan: "The release then needs a new revision").
- Legacy revisions cannot be approved retroactively; approving legacy content means drafting a new revision.
- Releases are readable by all authenticated staff (as the old release history was); internal notes are internal to staff, never to recipients.
- No automatic retries for campaign deliveries: an `unknown` outcome could be a delivered message, so only explicit retry of `failed` rows exists.
- The old `/api/software-updates/` endpoint was removed rather than kept read-only: its data now appears as legacy releases, and a second write path with a named approver would contradict PRD §8.1.

## Limitations

- Real sending is not implemented or authorised: only the console/file email backend and synthetic `example.invalid` recipients. Provider acceptance is recorded as `accepted`; bounces/delivery events are not tracked.
- The signup API adapter is a stub that fails visibly until the contract arrives; eligibility rules are not defined.
- Reconciliation is a manual note; no provider-log lookup exists.
- `e2e/config_features.py` still drives the removed Push Update page (it also used pre-WP10 nav labels and was already stale); WP14 owns the E2E suite.
- Capability grants have no admin UI in this work; grants are made through the existing accounts services/admin.
- No Graphify graph exists at the workspace or `fcops/` root; no graph update was applicable.
